# 全仓职责与柔性扩展重构

**起点**　`architecture-cohesion-extensibility`。源码规模基线 `cbea08e`，行为基线 `b500cbe`，工程与终审要求由同目录 [窗口纲领](outline.md) 规定。每阶段收口后检查代码、文档和数据，再重新盘点全仓并调整后续阶段。交付保留完整未提交工作区。

## 阶段安排

### Stage 1　梳理交互与状态所有权

从公开 CLI、原生 worker 和 C++ 命令追出三条主链。采集把原生调用与物理证据写成录制，编译与入库把合格观测变成可复用资产，预测消费资产与 workload。验证独立读取原生观测，通过窄适配口取得框架与平台的证据合同。交付逐域规模基线、耦合点与下面各阶段的交接定义。

### Stage 2　合并采集策略与会话生命周期

宿主工作流按缺口决定采集需求。框架适配贡献规则与切点，worker 按注册的模式启动原生探针。会话统一选择候选、分组、累计失败与成功尝试、发布读回。相同优先级的歧义和无效原始数据保持拒绝，具备其他候选的方法缺口才回退。已核验的录制和产品由库接手。核对公开入口、规则选择与预算恢复，真机回退与增量预测在 Final Stage 一次验收。

### Stage 3　整理原生控制、框架观测与平台归属

SGLang ABI 持有符号和接入版本，共享层持有原生配置、批次与资源合同。按调用、张量与模型分割、缓存与 PD、原生服务生命周期拆分观测和控制。PyTorch 负责本地张量与 Gloo 协议。Ascend 解释端与独立参考端共用原始只读索引，各自判定来源和效应。按 Docker COPY 边界核对两类 worker 的依赖，并在留存的 TP1、TP2/TP8、PD 输入上比较影响到的解释和取证入口。 迁移框架专用 CPU 声明加载，检查平台的延迟组件注册路径。按物理区间、语义端口与提交等待三个所有者继续整理 Ascend 解释器。

### Stage 4　理顺三条验证路径

读取与资格核验一次后，把配对、因果和固定图成本归到单一所有者。时间条件注入继续使用独立来源与唯一身份，物理时钟保留精确有理数认证。把能从已核验事实求出的结构检查声明为独立检查项。围绕留存 TP1 与 PD 核对配对计数、主动资源状态、消息序及固定图归因和自主评分。

### Stage 5　核对 C++ 与跨语言合同

围绕 C++23 核心的模板绑定、图依赖、资源、时间和成本求值消除真正重复的装配与分发。保留平台与框架代码在适配器下，采用同一发布的模型与特征合同。由最终 modeling Release 构建和模板、成本点、固定图与闭环预测对照验证。

### Stage 6　完成可读性和公开文档

逐域审查调用关系、长模块、嵌套及逻辑分段，校验英文注释、高价值说明和模块职责。同步 README 与静态设计，仅描述当前接口。每域核查代码、构建路径、维护边界和不宜合并的协议，记录改前改后指标及原因。建立冻结快照供 Final Stage 共用。

### Final Stage　冻结源码并完成验收

1. 绑定 `src/` 逐文件与汇总 SHA-256，完成越层、循环、缺失导入、代码墙、规模、Ruff、字节码检查。
2. 在 modeling Docker 构建 C++ Release，运行宿主源码、sdist 转 wheel、定向安装和可编辑安装的公开入口。用正式构建脚本重建和核验采集、控制双镜像。
3. 从独立归档输入重新执行 `b500cbe` 离线矩阵，比较四目标轨迹、发布、时延、空库缺口、库资产、四类样本、固定图成本、PD 对照和 TP2/TP8 资格。
4. 在全窗口预算内运行新注册规则的优先级回退、入库与预测，另用隔离的来源与目标实测 Qwen3-8B TP1 服务闭环。采集前核算剩余额度，按真实尝试保留测量、费用与资格。最终按源码快照归档审计矩阵、扩展证明、构建、真机账本和离线对照。
5. 更新阶段状态与交付记录，保留工作区供 AGY 终审。

## 阶段演进与 Bigger-Picture Overview 记录

### Stage 1　从公开入口确定重构切面

采集与预测经过宿主路由和持久库，控制与采集进程依镜像声明选择原生入口。设备事实沿平台原始索引进入解释和独立参考。两条流最终都依赖 C++ 的图、执行和成本合同。盘点显示采集互斥需要先拆除，下游过载集中在原生观测和独立验证。由此把原生适配、验证、C++、可读性与冻结验收分开。现有工作区已包含部分下游职责拆分，分别在所属阶段审查和收口。

### Stage 2　核对优先级、资格与预算边界

采集方式现在以安装包内的规则和探针贡献接入。同一宿主会话持有顺序、各次费用与获胜录制，入库读取归属已核验的录制。公开 CLI 的零额度运行已触发缺结构来源、选择两遍 CPU 探针、预算拒绝的完整准备分支。下游盘点发现拆分后的平台能力仍由字符串路径延迟加载，Stage 3 将核对注册目标及镜像可达性，并检查设备区间与端口的所有权。真机运行与最终证据绑定留在 Final Stage。

### Stage 3　沿独立证据检查解释与控制的耦合

原生符号、观测和虚拟控制职责已拆开，Ascend 的参考选择由后端声明直连不同所有者。开发回归先比较 TP1 和 TP2 的代表 rank，留存矩阵的全部原始输入在冻结后统一验收。全仓复查显示剩余最大模块在固定图参考，验证需要分离工作服务、时间线和边界归因。Stage 4 将补齐这些所有者及独立检查插件，再对照现有报告。

### Stage 4　修正固定图的坐标交接

全仓复查确认，同一原始运行时记录用于两种坐标。SDK 队列按计数器顺序归属，固定图的等待、队列通知和内核唤醒按 RAW 纳秒解释。平台独立参考明确输出两种视图，固定图保留现有归因口径。结构检查可从安装包贡献，基线差异与缺采结果仍按原结论记录。Stage 5 将着重整理跨语言表达式、模型与执行服务的分发，验证同时覆盖模板标识和预测数值。

### Stage 5　确认跨语言共享求值边界

modeling Release 验证表达式登记、图拓扑和执行服务的调整。全仓复查显示 Python 所有模块已降到过载线以下，剩余工作集中在大型事务的阶段划分、函数内代码墙和过期源码路径。Stage 6 先抽出能独立讲清的计算或生命周期，再逐域整理逻辑段落和注释，最后同时核对 CLI、镜像 COPY 与文档位置。

### Stage 6　完成事务拆分并冻结源码候选

全仓复查沿注册规则、录制、双库、控制和验证重走责任链。设备通信与跨调用数据各有一处所有者，CPU 载荷对照使用已配对的消息身份，原生服务生命周期保留原始时钟与清理职责。静态文档按当前物理目录描述入口。终验固定工作区源码和镜像，再并行完成打包及离线对照。真机按同一物理设备顺序运行，单独核算训练、留出及局部更新的实际来源和费用。

### Final Stage　按冻结内容交接终审

全仓复查从源码快照追到每个运行入口。C++ 语句分段通过同二进制核对，两个镜像从冻结上下文重建后身份一致。训练、结构留出和轻量时延留出各有独立录制，验证分开核对三种路径。扩展对照仅增减三份贡献模块，保留原规则、编排与发布代码身份。离线对照保留基线已有资格和失败结论。工作区及采集账本和对照证据一并交 AGY 核验。
