# 全仓架构重建、双模式采集与性能模型绑定

**已关闭**（提前结束，2026-11-23）。第 17 轮持续流量验证保留开发证据，第 18 轮同版本验收未开展。两轮均记为未完成。

开始日期为 2026-11-21。目标是重建 Prologue 的正式工作流，使用户能在单卡或完整拓扑上按需采集模板与性能数据，并通过跨模型、跨配置、跨请求的对照确定预测的适用范围。

## 用户流程与交付边界

用户给定固定模型、配置集、请求 workload 集、采集模式、可用设备和预算。系统检查已发布资产，汇总缺少的证据，选择原生采样任务，用实际观测建库或拟合，然后从目标初态运行预测。结果能解释每次采集为什么必要、每项成本来自哪里、哪些结论仍受证据限制。

| 采集模式 | 实际运行与证据 | 对目标预测的意义 |
|---|---|---|
| 单卡 | 整个采集任务仅能访问一张物理卡。按目标逻辑拓扑顺序执行必要的代表角色，在原生分片上取得本地模板和成本样本。 | 依据角色、载荷、端口和协议推导跨 rank 连接。跨卡时延与争用暂通过外接成本模型预测，记录来源和适用拓扑。模型或必要对端条件缺失时标出受影响的工作和动态结果。 |
| 完整 | 在目标拓扑运行全部真实参与者，观察本次执行的角色、连接和同步。 | 取得真实执行拓扑，对具有独立测量边界的工作采样。正式建库和留出评价各用已明确用途的案例。 |

逻辑拓扑决定哪些 worker 参与计算。采集模式决定它们怎样放到物理设备上，观测窗口决定本轮给哪些 worker 开启详细 profiler。代表角色可以为同等角色提供结构模板，跨卡通信服务时间另需同场物理证据。两种模式都可以使用定向采样。预测只读取目标输入和发布的资产。NVIDIA 本窗交付目录、文件职责和接入合同，设备实现及真机验收归后续窗口。

## 目标代码布局

自有业务代码按维护职责归入 `src/prologue/`。R1 要把下面的边界落实到具体源文件、Python 包、CMake 目标、Docker 镜像和命令，后续轮次可按实际消费者修订布局。

| 模块 | 拥有的规则和文件 |
|---|---|
| `app/`、`workflow/` | 前者负责命令、具体框架与平台的装配、容器和进程启动。后者负责用户任务的先后顺序、预算、恢复与发布。各进程按同一合同读取模型、配置和 workload，框架专属字段由相应适配器解释。 |
| `acquisition/` | 消费模板和性能层给出的证据需求，选择角色和采样方法、合并任务、核对实际命中。框架负责让原生代码到达指定工作，平台负责观测。 |
| `graph/`、`templates/`、`serving/` | 分别负责观测到粗图、模板生产与实例化、原生控制同模拟资源和时钟的交互。C++23 拥有共同算法。按产物和消费者重新划分现有的建图、模板生产和执行文件。 |
| `performance/` | 拥有工作身份、服务区间、特征、模型适用域及绑定。Python 负责取样后的拟合与模型发布，C++23 统一判断成本覆盖并求值，正式预测、补采规划和固定图对照共用该判定。 |
| `integrations/` | `frameworks/sglang/` 集中原生角色、模型分片、语义插桩和控制。可共用的张量与进程组事实放在 `runtimes/pytorch/`。设备部署、运行时记录、校时及原生采集桥放在 `platforms/ascend/`。确实同时依赖框架与硬件的行为在具体组合处装配。 |
| `verification/` | 分开维护真实参考提取、结构对照、固定图性能验证和自主预测评分。验证调用公共计算，独立参考保留原生依据。`example/` 负责场景构造、留出和矩阵编排。 |

**先判断改动归核心还是适配层。** 如果原生入口换了，但交出的角色、工作、端口及测量条件相同，改动应止于取得这些事实的适配器。给定这些事实后，模板如何归一化、端口如何连接、成本是否覆盖目标特征，由公共层各自的所有者决定。当新的原生行为会改变执行、成本或测量资格，且现有合同表达不了它时，一起修改合同、提供该事实的适配器和实际消费它的模块。

- **单卡分片。** SGLang 解释模型怎样切分、逻辑 rank 承担哪些层以及 KV 在哪里。采集和原生控制都要读同一种 SGLang 页布局时，共用 SGLang 适配器中的一份解释。模板层消费声明的布局和端口，图层按端口声明的参与者、载荷和依赖连接生产者与消费者。
- **定向计时。** 框架适配器让工作在目标状态下实际发生，平台适配器提供工作时间、时钟和测量依据。性能层决定哪些区间和特征能用于模型，采集层据此安排原生会话。替换平台计时 API 时，已有工作身份和服务区间能表达新观测，就可以沿用同一套模型选择与验证流程。

预定的 NVIDIA 接入点是 `integrations/platforms/cuda/`。部署文件负责设备可见性和启动条件，活动读取文件把设备工作、stream 和同步记录交给共同观测合同，时钟文件给出统一时间及不确定性。需要 SDK 的原生桥与该平台共同构建。R1 要用 Ascend 的实际调用核对这些文件的输入输出，R4 再从预测与验证两端检查依赖。创建 CUDA 实现文件的时点是后续实际接入。

## 四轮重构的最低工作量

每轮审查范围均为该轮起点的全部自有业务源码，加上本轮增删项及相关构建、打包、示例和产物合同。按模块记录已审查数与总数，要求覆盖 100%。**实质改造另按职责链计数。** 一条链从生产者追到最终消费者，有可核对的所有权、接口或执行路径变化，并清除被替代的逻辑。单纯搬文件、排版、撰写说明或重跑案例只记入相应工作记录。同一改造只计一次。

**用一次实际变更检验分层。** 每轮收尾在已有日志中选一项实际修改，指出维护这条规则的目录和文件、读取它的调用方，以及实际删去的重复路径。如果同一条角色判定仍要在规划器和模板选择器同步修改，或同一成本适用条件仍由 Python 与 C++ 分别维护，这条链继续整理。确实要跨层改动时，指出双方需要交换的事实及其消费者。可以由此合并、拆分或重写文件，目录名应能帮助维护者直接找到规则的所有者。

| 轮次 | 本轮必须实际完成的改造 | 最低开发回归范围 |
|---|---|---|
| R1 | **3 条**。任务到设备部署、框架语义到平台标记、样本复用到共同拟合各完成一条。核对起点的 232 个 Python、C/C++ 源文件及其装配。 | 完整模式下 Qwen3-8B TP1 和 TP2。 |
| R2 | **3 条**。目标需求到已有资产选择、原生任务到预算与中断恢复、资产发布到预测与报告各完成一条。 | 完整模式下 TP1 和一个多角色配置。另从公开入口走通冷建库、零补采复用、观测完成后的恢复。 |
| R3 | **3 条**。物理部署到逻辑角色观测、两种来源到模板与调用绑定、两种来源的成本证据到共同查询及验证各完成一条。 | 两种采集模式分别覆盖 TP8、TP2 × PP3、TP4 × EP4。 |
| R4 | **4 条**。目标工作到样本与模型绑定、覆盖与求值到规划和执行、原生与派生产物到发布和回收、独立参考到三条路径的诊断和评分各完成一条。 | 两种采集模式分别覆盖 TP2、PP3 和 PD，包含两种已接入的性能模型族。 |

表中每个“配置 × 模式”至少使用一个开发 workload，运行真实时间注入的结构对照、固定真实图的性能对照和自主闭环，保留三份结论。早期轮次使用当时的正式成本资产，分别标明已有成本缺口和本轮引入的回归。F1、F2 也分别用两种采集模式做三路对照。F1 选择 TP2 及一个有不同职责角色的拓扑，F2 选择能实际触发两种模型族的工作。

**未达标的处理。** 实施中一旦发现预计达不到门槛，当批在 `log.md` 记录应做数、实做数、具体缺项、原因及源码或运行证据，在 `status.md` 标明影响、补足动作和复验条件。阶段收尾核对全仓审查覆盖、实改数、三路验证覆盖三个分母。若某条链已在基线中完全满足要求，记录保留依据，实改数按实际计算。可改做解决同类问题、跨模块影响相当的职责链，保留原项、替代项和理由，原功能及验证要求仍须核对。仍有差额则保留“未达标”及原因，继续补足或明确修订范围。

## 实施阶段

前半程按 **R1 → R2 → F1 → R3 → F2 → R4** 交付架构与功能，共 39 个片段。后半程 V 分四个里程碑，第 01–17 轮各验证一个机制，第 18 轮用同一交付版本做跨轮验收。首轮独立实验沿用原编号 V.1–V.6 存档。历史片段和新验证轮次分别计数。

各轮以已有证据为起点，先核对生产者、消费者和适用边界，再集中修改、统一构建。轮内按内容摘要冻结代码与资产。前半程各阶段、V 的四个里程碑及最终验收是仓库审查和分层提交推送的边界。`status.md` 维护当前交付与恢复起点，`log.md` 记录有实质进展的工作批次。

### F1 · 实现单卡与完整两种采集模式

两种模式共用观测合同、模板构造及成本样本的消费入口。单卡的差异集中在取得观测这一段。框架适配器驱动原生逻辑角色、分片及批次状态，平台限定可见的物理设备并记录实际工作。扩展一种并行策略时，先复用已有的本地执行、载荷交接和端口连接，仅在原生职责或数据语义确有差异处增加实现。先在 Qwen3-8B TP2 上完成真实本地分片、Prefill 写入及 Decode 读取 KV、跨通信端口继续执行三个环节，再判定可推广范围。

### V · 四个里程碑与最终验收

第 01–17 轮各交付一个结论，记录支持它的模型、配置、请求和两种采集来源。第 18 轮检验这些结论能否在同一版本上同时成立。沿用 SGLang、Ascend、dummy 权重和预先给定的生成长度。新模型各自采集适用的模板和成本，跨模型验证的是同一工作流和变换规则的适用性。

#### 每轮的开发回归、独立验证与返修

1. **开发回归。** 先写明本轮唯一要判断的行为、待改变的因素及其原生观测位置。用已公开案例、训练外的开发请求和相邻配置，分别覆盖正常行为、边界和对照条件。以实际观测确认进入了目标分支，并在开发数据上走通主验收路径。例如验证混批要看到同一批中确有 Prefill 和 Decode。若已有参考足够，复用它离线开发。
2. **独立验证。** 开发回归能说明该怎样判定成败后，冻结代码、镜像、模板、成本与外接通信资产、评价器、指标分母、额度及抽样规则。每个承诺的模型与配置至少登记一组新请求，覆盖本轮表中的成对条件。冻结后一次生成输入，在取得真值前封存输入摘要、种子或真实流量行段及实际分母。开发、训练、历次已揭盲案例和最终留出分开。成对实验可跨模型共用同一到达和长度序列。冻结批次中保留包括报错、资源耗尽和未触发在内的全部结果。
3. **返修与交接。** 以第一处可解释的分歧定位到原生参考、适配器、模板与控制、成本绑定或评价器。共同根因集中修改，再用原例和至少一个共享机制的不同案例复验。已揭盲案例转为开发回归。需确认修复后的独立结论时，只为受影响范围取新的留出输入，可并入覆盖该机制的下一轮或最终验收。一次发现两个独立根因时分别指定责任轮，必要时拆小轮并注明其阻塞项。本轮主判据有独立证据才记为完成。修后待独立确认和仍受阻分别列出原因，依赖该结论的轮次等确认后接续，其他已具备前置的轮次可继续。

独立目标按**物理目标、请求、评价项**分别记数。一个物理目标由模型、完整配置、初态和请求序列确定，在同一目标上取得一份详细原生观测和一份独立轻量计时，两种采集来源共用它们。若本轮登记 N 个物理目标，计划参考为 2N 份，评价为 6N 项。每轮预算分别列训练与补采、详细及轻量启动、设备时间、仿真墙钟和保留空间，按实际尝试计费。重用同一真值重算预测时只增加离线运行次数。

|---|---|
| 真实时间注入，核对结构 | 逐工作核对实测时间及必要外部就绪条件，控制器自行组批并展开模板。按请求、阶段和角色比较工作、参数、端口、依赖及资源效果。仅有上下界的端点标明来源与影响，缺少独立测量时只报告可比范围。整轮观测窗口只能约束端点，不能作为逐节点实测依据。 |
| 固定真实图，核对性能 | 固定真实批次、工作、资源、依赖及控制器实测的外部输入交付。用实测服务时长重现端点，交付前的本地进度独立核对。再只替换预测成本，报告新增输入等待及逐类恢复实测时长的影响。同步或重叠工作共同影响端点时单列，分别恢复的影响不可直接相加。 |
| 自主闭环，核对请求 | 正式预测只读取目标输入和独立发布的资产，自行生成批次和时间。评价端另核对轻量参考、稳态与训练隔离资格，比较 TTFT、TPOT 和吞吐。参考失效也保留预测完成位置及首个缺口。 |

每轮独立记录两种来源的三路结果，以本轮主判据决定交接。已取得可解释的误差可以推进归因，最终精度达标另由第 18 轮判断。报告列出计划、实际、完整匹配、局部可比、确认差异、缺证和阻塞的项数，以及每个指标的计划与可评分请求数。核心与单案例验证负责共同语义，框架与平台适配器提供原生切口、角色和时钟事实，场景构造、抽样与跨案例汇总归示例编排。

#### 第 18 轮 · 同一版本的跨轮验收

1. **选定最终目标。** 四个里程碑交付后，在同一版本上纳入原八种配置、Qwen 与 Mistral 同宽 TP 和同一多角色拓扑的成对对照、同一 MoE 开关 EP 的对照，以及经开发确认的第二个 MoE。保留 Llama TP2 作为已有机制的新组合。普通 TP 与多角色或调度组合中，各安排至少一组新的 100–200 请求负载。共享合同或评价器返修过的范围明确入选，其中 Mistral PP3 的单页 Prefill 及 Qwen3 TP4 × EP4 的双成员原页 Decode 要求实际触发对应分支。
2. **封存后一次收齐。** 先登记逐目标的两个来源、三条路径、主比较、预算、失败口径和逐请求分母，再封存资产和新输入。开发、拟合、前 17 轮已揭盲的输入或同一段真实流量均不计作最终新留出。共同观测可在本轮成对比较中复用。冻结批次收齐后统一归因，修后如需发布新的独立结论，保留此次报告并对受影响范围另取新例。
3. **按证据交付。** 对每个模型、配置和来源分别报告结构覆盖、固定图的端点与成本误差、自主闭环的 TTFT、TPOT、吞吐，以及采集和预测开销。多角色差异按 rank 与职责定位。TTFT、TPOT 分别按合格请求计算 MAPE，汇总到来源模式时按各指标的有效请求数加权，同时公布覆盖率。两项均低于 6% 才能对相应范围声明精度达标。只有一个输出 token 的请求单列 TPOT 不适用，未取得可评分请求时报告分母为零。缺参考、未触发或阻塞的目标始终保留在计划分母。

原八种配置及其短请求和错峰对照继续覆盖。原方案为单批复验登记的 16 个负载范围原地留档，新轮次按上述分工另行冻结和计费。旧登记中的 32 次参考启动额度属于原单批方案。[原八种配置与冻结范围](../../../data/architecture-acquisition-performance/v/scope.json) · [原单批复验预登记](../../../data/architecture-acquisition-performance/v-revalidation/inputs/specification.json)

## 阶段维护和窗口收口
