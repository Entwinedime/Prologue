# 窗口工作文档与推进规则

本文件是 `docs/windows/` 下所有活动窗口与历史窗口的唯一权威规范。用户最新明确指令优先；规则服务于简洁、可恢复、可核验的迭代推进，不据此新增检查平台、审批流程或平行账本。本文是静态规范，不记录具体窗口进度。

## 一、定位、边界与目录组织

- **目录命名**：每个窗口位于 `docs/windows/YYYY-MM-DD_<purpose>/`。`<purpose>` 使用英文 `snake_case` 表达稳定的功能、重构或验证职责；同一主题允许跨多个会话持续维护原目录，不按单次对话新建窗口。
- **并发控制**：原则上同时只维护一个活动窗口；确有独立并行任务时才增开活动窗口。
- **文件组成**：每个窗口维护 `plan.md`（计划）与 `log.md`（日志），需要跨会话独立进度快照时增加 `status.md`（状态）。不另建总结、review、evidence 等平行正文，也不为拆分文件新增导航目录或历史备份（用户明确要求时除外）。
- **文档边界**：
  - **跨层不引用**：窗口文档不写指向静态设计文档或项目主工作流的 Markdown 链接，也不写“见主计划”“按某设计文件第几节”或路径形式的内容依赖；每份文档独立说明读者所需结论。可以链接仓库源码、配置和实际证据；同窗口内确有必要时可引用，但不建立密集互链。
  - **不复制正文**：窗口只维护自身范围、任务、实时快照和实施事实，不抄录静态设计文档的完整合同或主工作流。
  - **一处维护一个问题**：`plan.md` 维护目标、范围、阶段轮次、交接与关闭标记；`status.md` 维护活动期间的唯一恢复快照；`log.md` 维护按时间发生的事实与证据。三者不重复维护同一份滚动进度或待办清单。
  - **未实现接口隔离**：尚未实现的命令、参数或入口只出现在窗口 `plan.md`，不提前写入静态操作说明。

## 二、双智能体分工与协作机制（AGY × Codex）

本项目的窗口迭代采用 **AGY（Gemini）维护窗口与规划审查 + Codex 负责实现交付 + 用户把关确认** 的协作模式，明确维护权与质量约束，发挥双方优势并抑制典型问题。

### 1. 角色定位与优势分工

| 角色 | 核心优势 | 职责边界 |
| --- | --- | --- |
| **AGY（Gemini）** | 长上下文全局视图、跨层架构分析、边界裁决与全链审查 | 唯一维护窗口规范与各窗口生命周期；编写与修订 `plan.md`；核验阶段交付、做跨模块审查与根因复盘；提供边界清晰的 Codex 执行指令；裁决放行下一阶段或关闭窗口。 |
| **Codex** | 高吞吐多文件编码重构、精确落实明确合同、长程构建/运行/排障闭环 | 在既定计划与约束内完成 C++/Python/Docker 代码实现、必要构建与公开入口/实机验证、分层提交推送；按批次向 `log.md` 如实记录事实与证据，并刷新 `status.md` 的执行态快照。 |
| **用户** | 最终需求裁决、资源与风险授权、阶段把关 | 审定关键计划与高风险重构、按约定启动或恢复 Codex、在暂停点通知 AGY 复查并批准跨阶段推进。 |

### 2. 窗口文档维护权边界

- **AGY 拥有窗口规划与裁决权**：本规则文件、各窗口 `plan.md`（目标、范围、阶段轮次、验收判据、暂停点、关闭标记与修订）以及关窗总结均由 AGY 维护。双方以当前窗口的 `plan.md`、`status.md`、`log.md` 作为唯一交接载体，不额外建立平行任务单或二次汇报文档。
- **Codex 仅写实施事实**：Codex 执行期间只更新活动窗口的 `log.md`（实际改动、验证、失败与限制）和 `status.md` 的执行态字段（更新日期、已完成轮次、基线 commit、当前轮次进展、可依赖事实与已知费用），**不得擅自修改 `plan.md` 的目标、非目标、验收门槛、删改清单或约定暂停点**，也不得通过缩窄范围或新建平行文档掩盖未完成项。
- **遇阻回传而非自行降标**：Codex 实施中若发现计划前提不成立、上游合同缺失或原路径受阻，须保留现场证据并在 `log.md` / `status.md` 写明阻塞原因后停止，交由 AGY 复盘并修订 `plan.md`。

### 3. AGY（Gemini）制定计划时对 Codex 负面问题的抑制要求

AGY 编写 `plan.md` 与执行范围说明时，须针对 Codex 在自主长程编码中的常见负面倾向提前设防：

- **抑制“局部打补丁、只增不删与双轨残留”**：每轮指定唯一状态或规则所有者，并列出**显式删除清单与禁止保留项**（写明被替代后须整段删除的旧函数、旧文件、旧入口或旧分支，禁止保留兼容别名、兜底 fallback 或转发 wrapper）；在接口扩用前安排独立收紧轮次，把冗余清零纳入硬验收。
- **抑制“跨层泄露与抄近路耦合”**：写清模块归属与**依赖方向红线**（如公共核心与工作流层禁止引入具体框架名、硬件后端或特例分支）；若原生能力超出既有合同，先单列公共合同修订再接适配器，防止为图省事把特例塞进公共层。
- **抑制“局部 diff 视野遗漏上下游与跨语言同步”**：每轮写清 `交接：输入 → 交付物 → 使用者`，显式列出受影响的 C++/Python 双侧生产者、消费者、构建配置与公开入口；阶段收尾要求沿职责链追踪未改动但受影响的代码，不只看 diff。
- **抑制“自洽幻觉、降标凑通过与私建自测脚手架”**：写死可观察验收判据、验证层级与必须保留的反例；明令禁止手调系数凑精度、禁止用静态推导或给定耗时冒充运行或精度通过、禁止私自新增独立 test 工程、mock 或自测脚本。
- **抑制“同错死循环与预算失控”**：对涉及构建、容器或硬件采集的轮次写明最小验证范围、费用口径与**失败熔断条件**；同一根因或同类缺口反复失败且无新事实时立即止损并记录证据，禁止无限微调重试或盲目扩跑实验，转交 AGY 做根因与方法复盘。
- **抑制“范围蔓延与越权跨阶段推进”**：单次交给 Codex 的任务切片必须可闭合、可独立审阅，显式写明**本批非目标**（禁止顺手重构无关模块或全仓重排）；在每阶段收尾及高风险改动前设置硬性**约定暂停点**或**人工确认门控**，明确要求完成当前边界检查与分层推送后即停止。

### 4. 协作闭环

1. **规划与确认**：AGY 基于最新代码与证据编写或修订 `plan.md`（高风险任务置顶注明人工确认门控），界定本批切片范围与暂停点，并给出配套的 Codex 执行说明；经用户确认后进入实现。
2. **实施与留证**：Codex 严格按 `plan.md` 与工程约束完成实现、构建、必要验证与分层提交，同步更新 `log.md` 与 `status.md`；遇到人工确认门控、到达 `**约定暂停点**` 或触发失败熔断时必须立即停止并汇报，不得自动越权推进。
3. **审查与迭代**：用户通知 AGY 检查本批提交、全链影响、证据真实性与状态资格；AGY 给出审查结论，决定放行下一阶段、追加返修、修订计划或关闭窗口。

## 三、计划文档（`plan.md`）

`plan.md` 定义本窗口的目标、范围、阶段与轮次安排、验收条件及关闭结果。

### 1. 顶部元信息

- 一级标题：`# <窗口主题>`。
- **关闭标记位**：活动期间留空；窗口关闭或取消后紧接标题下标注 `**已关闭**`。
- **人工确认门控**（按需）：若整份计划或特定阶段要求用户手动确认后才可实施（例如高风险重构），须在顶部显式声明，执行方不得在未经确认前自动修改或跨阶段推进。
- `**开始日期**`：`YYYY-MM-DD`，必要时注明开发分支与开窗基线提交。
- `**目标**`：用简明语句说明用户可观察的最终交付目标及关键里程碑。

### 2. 正文必备内容

1. **范围与非目标**：明确覆盖范围、依赖前提及明确留给后续窗口的能力边界。
2. **实现方法与代码归属**：说明端到端流程、核心改造边界和受影响模块的职责落点（可用简洁表格或流程图表达）。
3. **阶段与轮次拆解**：
   - 将窗口划分为明确的交付阶段（例如 `M1–Mn`），阶段内拆分为离散、可核验的轮次（例如功能轮 `R01–Rk`，必要时穿插独立重构轮 `F01–Fj` 或集中重构阶段）。
   - 每个轮次写明三项内容：
     - **为什么做**：本轮要解决的具体阻塞、问题或冗余。
     - **改动与验收**：要改动的职责链、具体验证输入与可观察验收判据。
     - **交接**：明确 `输入 → 交付物 → 使用者`。
4. **完成/停止条件、关键风险与资源约束**：写明验收门槛、采集或算力预算口径、重构计数与未达标处理方式，以及阶段维护与交付边界。

### 3. 进度归属与计划修订

- 单独设置 `status.md` 时，`plan.md` 不混入滚动实施进度、阶段状态或实时消耗；没有 `status.md` 的小窗口可在 `plan.md` 开头保留简短进度。
- 计划服务于实际工作，不机械沿用初稿。按真实证据拆分、合并、重排或删去重复任务时，须记录调整原因、影响和未完成事项，不得默默取消用户要求或降低完成标准。
- 实施中预计达不到既定门槛时，按实际记录应做数、实做数、缺项、原因及证据；仍存在差额时保留“未达标”状态，继续补足或经明确修订处理，不得降低判据宣称完成。

## 四、状态文档（`status.md`，按需设置）

跨会话、多阶段或双角色协作的窗口可单独设置 `status.md`，集中维护活动期间的进度、基线、已验证范围、限制和下一步起点。

### 1. 内容与结构

`status.md` 只保留恢复工作所需摘要，不复制完整计划、日志或实验报告，也不成为新的文档层。常规字段如下：

- `**更新日期**`：`YYYY-MM-DD`。
- `**进度**`：已完成轮次 / 总轮次（及完成率）、已收尾阶段数 / 总阶段数、开发分支与当前恢复基线 commit。
- `**约定暂停点**`（按需）：明确何时暂停推进、暂停前须完成的交付动作以及等待谁恢复确认。
- **阶段表**：逐阶段列出轮次范围、已交付分母及当前状态摘要。
- `**可依赖的事实**`：经证据确认、后续可直接依赖的结论，以及尚未完成的明确限制。
- `**当前轮次**`：当前正在推进或待收口轮次的实际状态、阻塞点与关键证据入口。
- `**已知费用**`（涉及采集时）：核心卡时、冷/热会话增量及与预算目标的对照。

### 2. 状态资格与维护规则

- 状态严格按实际资格区分以下七档：`待做`、`实施中`、`源码已改待验证`、`限定范围验证`、`待交付`、`完成`、`暂停`。
- 用新结论直接替换当前快照，旧过程留在 `log.md`。篇幅增长时先替换过时结论、合并重复，不挤成长段或无限附加“最新情况”。
- 约定事项不勾选为实现任务，未知风险不自动扩大门槛。

## 五、日志文档（`log.md`）

`log.md` 按日期正序记录实际发生的工作、决策、复盘与证据；同日多条按发生次序排列，不补造具体时刻或另加流水号。

### 1. 标准条目格式

```markdown
## YYYY-MM-DD — <阶段或事项>：<本批主题>

**范围：** 对应的阶段/问题及本批边界，必要时注明基线。

**改动：** 实际修改、审查发现或已作决定，以及必要原因。

**验证：** 方法、输入/覆盖范围、实际结果和证据位置；没有执行验证时明确说明。

**结论与限制：** 本批已证明的结果、未验证部分及影响后续工作的缺口。
```

### 2. 记录规则

- **精简与证据**：四个字段各司其职，通常各一至三句；多项独立验证可在“验证”下列短列表。证据写必要路径、关键命令或结果数值，不粘贴完整输出、巨量 JSON、环境清单或重复配置。详细运行数据保存在 `data/`，临时验证材料明确标为临时位置；日志只保留复核入口、必要计数和口径。
- **粒度与命名**：一条对应一个有意义的工作批次。同一问题的连续修改和验证合并记录；有独立决策、重要失败、周期复盘或阶段交接时另起条目。标题写具体事项，不使用“最新进展”等无区分度名称。
- **区分验证层级**：严格区分源码检查、编译、条件运行、真实原生观察及独立验收。记录历史结果时注明是复核已有证据；未运行写“未运行”，不能将静态判断或给定耗时结果写成运行或精度通过。
- **不维护第二份滚动状态**：日志保留当时做了什么、证明了什么，不在文件开头维护滚动状态，不复制后续步骤或每日重复待办。“结论与限制”只保留本批产生或改变的事项。
- **不可覆盖历史失败**：影响范围、预算或结论的失败与取舍必须保留。整理时可合并同一批次的条目、压缩重复叙述，但不能覆盖历史失败，也不能把后来通过改写成早先已通过；纠正旧记录须说明纠正了什么。
- **复盘条目**：每次周期审查或提前复盘，在日志中简述已完成范围、共同根因及证据（区分逻辑覆盖不完整与方法问题）、应保留或删除的机制、下一批修改及最小验证依据；确认事实与待验证判断分开。
- **阶段启停条目**：阶段启动条目在“范围”记录起点提交，在“改动”记录本阶段及后续计划的调整；阶段收尾条目在“验证”记录关联代码审查、文档/数据整理检查与遗留处理，在“结论与限制”说明交付状态。最终交付提交及远端确认在下一阶段启动条目引用，不要求提交记录自己的 hash，也不为自引用反复补提交。
- **采集资源口径**：采集条目须注明本批会话/尝试数、实际覆盖及累计额度变化（失败、换请求和恢复不清零），并分别说明初始化/预热、有效观测、后处理、导出量、保留量及峰值；源码或文档条目不填无关资源字段。
- **避免空记录与形式工具**：无新工作不追加空条目，不为日志格式新增生成器、账本或自动检查平台。

## 六、阶段启动与维护交付

阶段是明确的维护和交付边界。功能编写结束后，仍须完成关联代码审查、仓库整理、代码/文档/数据检查及分层提交推送；全部完成后才成为下一阶段的基线。阶段收尾不能推迟到整个窗口最后一次处理，日常周期审查也不能代替阶段交付审查。

### 1. 阶段启动

- 以上一阶段已推送的最终提交为起点，核对项目现状、实际能力、遗留限制、可用环境和数据。
- 据此重新整理当前阶段的目标、范围、依赖、交付及必要验证，并检查剩余阶段是否需要拆分、合并、重排或删除重复任务。
- 窗口首阶段先明确筹备改动的归属和提交基线，不能把先前未提交内容算作本阶段成果。

### 2. 阶段收尾与三类检查

阶段结束时，从 Git 起点提交核对本阶段全部提交、最终工作区差异及未跟踪文件，分别完成代码、文档和数据检查：

- **代码检查**：沿修改影响到的生产者、消费者、调用方、配置、构建和产物追踪审查（范围包括未改动但受影响的代码，不只看 diff），逐项检查代码层次与适配边界、状态/资源所有权、正确性、表达风格和可删除/合并的冗余。可使用 Ponytail 等静态工具辅助，但不能以工具通过代替完整内容审查；确认问题和待验证风险分别记录，修正后的相关链路再核对。验证以静态推导及必要 Docker 构建/公开入口运行为主，收尾修正按影响范围复查，不逐阶段重跑整个独立验收矩阵。
- **文档检查**：整理过期描述、重复内容、阶段状态、职责边界、跨层引用与证据链接。证据被删除时取消可点击入口，必要历史结论注明不可复核；不重建旧账本或伪造当前验证。
- **数据检查**：核对适用环境、引用及保留范围；保留仍被使用的输入、正式资产、必要来源、验证证据及预算/恢复信息，仅清理本任务拥有且已确认无用的产物。
- **纯文档任务**：纯文档阶段或整理任务只检查文档，明确说明代码与数据是否受影响，不因此启动构建、采集、数据清理或恢复；交付仅说明本轮真实修改与检查，不把旧工作区 diff 全算作本轮成果。

### 3. 分层提交与推送

- 三类检查完成后，按可独立审阅的职责分层提交并推送开发分支，核对暂存内容及远端实际提交，再将交付提交作为下一阶段基线。
- 数据“检查完成”不表示提交数据，原有忽略范围保持不变。
- 提交或推送未完成时保留“待交付”状态和已有提交，不开始下一阶段实现；阶段状态、基线和交付事实沿窗口文档记录，不增加审批、自动检查平台或平行账本。

## 七、窗口关闭与取消

活动计划若仍有未完成范围，不能为了整理目录擅自关闭或取消；主工作流只留其概要，实施细节继续由该窗口维护。确认关闭、提前结束或取消时，按以下四步执行：

1. **在计划页标记关闭**：核对实际结果，在 `plan.md` 标题下标记 `**已关闭**`，注明关闭结论是完成、提前结束或取消以及关闭日期，按实际记录未完成的内容。
2. **向主工作流写自足总结**：包含日期和目标、主要修改与取舍、实际验证范围、结论与遗留项；保留影响后续判断的失败及证据，不复制完整日志。
3. **登记遗留去向**：将未完成事项明确记录为后续目标、范围外能力或待验证限制；确需继续执行时，另建有明确边界的新窗口。
4. **原地保留历史记录**：关闭后在原目录保留 `plan.md`、`log.md` 及已有的 `status.md`，作为历史记录。设计或工程约束发生变化时，独立修订相应静态合同。
