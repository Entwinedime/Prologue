# 窗口工作文档与推进规则

本文件是 `docs/windows/` 下所有活动窗口与历史窗口的唯一权威规范。用户最新明确指令优先；规则服务于简洁、可恢复、可核验的迭代推进，不据此新增检查平台、审批流程或平行账本。本文是静态规范，不记录具体窗口进度。

## 一、定位、边界与目录组织

- **目录命名**：每个窗口位于 `docs/windows/YYYY-MM-DD_<purpose>/`。`<purpose>` 使用英文 `snake_case` 表达稳定的功能、重构或验证职责；同一主题允许跨多个会话持续维护原目录，不按单次对话新建窗口。
- **并发控制**：原则上同时只维护一个活动窗口；确有独立并行任务时才增开活动窗口。
- **文件组成**：
  - **自主演进窗口（默认推荐）**：维护 `outline.md`（战略纲领，AGY 唯一维护，只读）、`plan.md`（动态执行计划，AGY 起草初版，Codex 在推进中按阶段动态展开与修订）、`log.md`（实施事实与全局审视日志），跨会话时增加 `status.md`（实时恢复快照）。
  - **传统分段窗口（兼容模式）**：不单独设 `outline.md`，仅维护 `plan.md`（由 AGY 唯一维护，含阶段暂停点）、`log.md` 与按需的 `status.md`。
  - 不另建总结、review、evidence 等平行正文，也不为拆分文件新增导航目录或历史备份（用户明确要求时除外）。
- **文档边界**：
  - **跨层不引用**：窗口文档不写指向静态设计文档或项目主工作流的 Markdown 链接，也不写“见主计划”“按某设计文件第几节”或路径形式的内容依赖；每份文档独立说明读者所需结论。可以链接仓库源码、配置和实际证据；同窗口内确有必要时可引用，但不建立密集互链。
  - **不复制正文**：窗口只维护自身范围、任务、实时快照和实施事实，不抄录静态设计文档的完整合同或主工作流。
  - **一处维护一个问题**：`outline.md` 维护战略目标、非目标、工程标尺、不可妥协红线、预算上限、终审门禁与关闭标记；`plan.md` 维护动态阶段拆解、交接路线与阶段演进记录；`status.md` 维护活动期间的唯一恢复快照；`log.md` 维护按时间发生的事实、验证与决策。四者不重复维护同一份滚动进度或待办清单。
  - **未实现接口隔离**：尚未实现的命令、参数或入口只出现在窗口 `outline.md` / `plan.md`，不提前写入静态操作说明。

## 二、双智能体分工与协作机制（AGY × Codex）

本项目的窗口迭代采用 **AGY（Gemini）维护纲领与终审把关 + Codex 端到端自主实现与动态规划 + 用户拍板授权** 的协作模式，明确权责边界，发挥双方优势并抑制典型问题。

### 1. 角色定位与优势分工

| 角色 | 核心优势 | 职责边界 |
| --- | --- | --- |
| **AGY（Gemini）** | 长上下文全局视图、跨层架构判据、防偷懒机审与终审裁决 | 唯一维护本规范与各窗口 `outline.md`（及传统窗口 `plan.md`）；起草初版动态 `plan.md`；在窗口终审或暂停点执行独立脚本核验、跨模块代码抽检与根因复盘；裁决放行、打回返工或关闭窗口。 |
| **Codex** | 高吞吐全仓重构、长程构建/验证/排障闭环、一线代码演进判断 | 在 `outline.md` 既定红线、工程标尺与预算内端到端自主完成架构盘点、代码实现、构建与公开入口/真机验证；**每阶段完成后执行全仓 Bigger-Picture Overview 并动态修订展开 `plan.md`**；如实记录 `log.md` 并刷新 `status.md`。 |
| **用户** | 最终需求裁决、资源与风险授权、终审放行与提交确认 | 审定窗口纲领与高风险方向、启动或调整 Codex、在终审后确认提交推送与关窗。 |

### 2. 两种窗口运行模式与维护权边界

- **AGY 拥有窗口纲领与裁决权**：本规则文件、各窗口 `outline.md`（战略目标、非目标、质量标尺、红线、预算、防偷懒门禁、提交纪律与关闭标记；无 `outline.md` 的传统窗口则对应 `plan.md`）以及关窗总结均由 AGY 唯一维护。
- **模式 A：全窗口自主演进模式（默认推荐，适用于全局架构重整与多子系统工程）**：
  - `outline.md` 对 Codex **严格只读**，严禁擅自修改红线、降标或扩预算；
  - `plan.md` 由 AGY 提供初始骨架，**阶段总数不固定**；Codex **有权且应当在每个阶段完成后执行一次完整的全仓 Bigger-Picture Overview**，跳出局部 diff 重新俯瞰全仓架构拓扑、模块交互与现状，据此动态新增、拆分、合并或调整 `plan.md` 中的后续阶段并持续推进，中途不设人工暂停点；
  - 默认支持**全流程零 `git commit` / `git push`**：Codex 全程仅在工作区修改，证据绑定最终工作区 `src/` 逐文件 SHA-256 清单与汇总哈希，全部完成后保留干净工作区交回 AGY 一次性全面终审，经终审通过并由用户确认后再统一分层提交推送。
- **模式 B：分段门控模式（兼容传统窗口，适用于高风险实验或需逐阶段裁决的任务）**：
  - 不单设 `outline.md`，Codex 仅写 `log.md` 与 `status.md` 的执行态字段，不得修改 `plan.md`；每到达约定暂停点即提交推送并停止交回 AGY 审查。
- **遇阻回传而非自行降标**：无论何种模式，实施中若发现纲领前提不成立、上游合同缺失或触发失败熔断，须保留现场证据并在 `log.md` / `status.md` 写明阻塞原因后立即停止，交由 AGY 复盘修订纲领。

### 3. AGY 制定纲领时对 Codex 负面倾向的抑制要求

AGY 编写 `outline.md` 与初始 `plan.md` 时，须针对 Codex 在自主长程编码中的常见负面倾向提前设防：

- **抑制“只改点名示例、回避全仓盘点”**：在纲领中明确列举的模块与坏味道仅作典型症状参考，要求覆盖全仓所有业务子系统并交付可机审的逐域审计矩阵（未改子系统须逐文件给出审计依据）。
- **抑制“为了凑文件数/行数做机械合并或制造密集代码墙”**：不设拍脑袋的硬性文件数上限或机械减行指标；改用单一职责、过载文件清零、杜绝函数体内超长连续无空行代码墙、以及动态柔性空行/注释参考区间配合终审抽检来保障可读性与内聚度。
- **抑制“局部打补丁、只增不删与双轨残留”**：明确唯一状态或规则所有者，要求彻底删除被替代的旧实现、旧入口与转发 wrapper，禁止套壳假灵活。
- **抑制“跨层泄露与抄近路耦合”**：写清模块归属与依赖方向红线（如公共核心与工作流层禁止引入具体框架名、硬件后端或特例分支）；若原生能力超出既有合同，先修订公共合同再接适配器。
- **抑制“局部 diff 视野遗漏上下游与渐进式丧失全局观”**：强制要求每完成一个阶段即执行一次全仓 Bigger-Picture Overview，沿职责链追踪生产者、消费者、跨语言边界与构建配置，再动态修订后续 `plan.md`。
- **抑制“自洽幻觉、降标凑通过与私建自测脚手架”**：写死可观察验收判据、验证层级与必须保留的反例；明令禁止手调系数凑精度、禁止拿静态推导冒充真机通过、禁止拿旧证据充数（须绑定最终工作区 SHA-256）、禁止私自新增独立 test 工程、mock 或自测脚本。
- **抑制“同错死循环与预算失控”**：明确有界真机预算（失败与重试不清零）及失败熔断条件；同一根因连续尝试 2 轮无新进展或预算耗尽立即止损交回 AGY。

### 4. 协作闭环

1. **建窗与起稿**：AGY 基于最新代码与证据制定只读 `outline.md` 与初始 `plan.md`（及 `status.md`/`log.md`），经用户确认后交由 Codex 启动。
2. **自主动态演进（自主模式）**：Codex 执行「阶段实现 → 三类自查 → 全仓 Bigger-Picture Overview → 动态更新 `plan.md`/`status.md`/`log.md` → 下一阶段」的自主闭环，直至完成全部阶段与终验（或触发熔断）后停机汇报；若为传统分段模式，则按阶段暂停点逐段交回审查。
3. **独立终审与收口**：用户通知 AGY 对交付工作区（或提交）执行独立脚本核验、防偷懒门禁检查、源码 Diff 品质抽检与证据 SHA-256 验真；AGY 给出终审结论，经用户确认后统一提交推送或打回返工，并按第七章关闭窗口。

## 三、纲领文档（`outline.md`）与执行计划（`plan.md`）

### 1. 纲领文档 `outline.md`（自主窗口必备，AGY 唯一维护）

- **顶部元信息**：一级标题 `# <窗口主题> — 窗口纲领（Outline）`；**关闭标记位**（活动期间留空，关闭或提前结束时紧接标题下标注 `**已关闭**`）；`**开始日期**` 与基线；`**交付纪律**`（如是否全流程零 `git commit`、是否无中途暂停点）。
- **正文必备内容**：
  1. **核心目标与工程质量标尺**：定义全仓适用的架构原则、扩展性标准、可读性/空行/注释要求及典型症状参考（明确非工作上限）；
  2. **不可妥协的红线与非目标**：科学/物理不变量、物理分层与跨层依赖边界、构建卫生与回归基线；
  3. **每阶段强制 Bigger-Picture Overview 机制**：明确要求 Codex 每阶段完成后俯瞰全仓并动态更新 `plan.md`；
  4. **AGY 终审防偷懒门禁、有界预算与熔断规则**：列出终审可独立复算的机审门禁、动态柔性品质抽检口径、硬件预算上限及止损规则。

### 2. 执行计划 `plan.md`（自主窗口由 Codex 动态展开；传统窗口由 AGY 维护）

- **自主窗口下的定位**：由 AGY 提供初始阶段骨架（明确**阶段总数不固定**），Codex 在完成首阶段全局盘点及每个后续阶段后，直接在本文件中增删、拆分、细化后续阶段（`Stage 1..N` 及 `Final Stage`），并在文末维护「阶段演进与 Bigger-Picture Overview 记录」。
- **每阶段必备要素**：
  - **为什么做**：本阶段要解决的具体结构耦合、刚性硬编码、过载或验证问题；
  - **改动与局部验证**：涉及子系统、预期重构后的抽象与交互边界、具体验证输入与可观察判据；
  - **交接**：明确 `输入 → 交付物 → 使用者`。
- **传统窗口兼容**：未设 `outline.md` 的历史或分段窗口，继续在 `plan.md` 顶部承载元信息、人工确认门控、关闭标记与完整验收门槛。

### 3. 进度归属与计划修订

- 单独设置 `status.md` 时，`outline.md` 与 `plan.md` 不混入滚动实时消耗；没有 `status.md` 的小窗口可在 `plan.md` 开头保留简短进度。
- 计划服务于真实代码现状，不机械沿用初稿。动态调整、拆分或增补阶段须说明架构依据与影响，且绝不得突破 `outline.md` 的红线、预算或降低验收门禁。
- 实施中预计达不到既定门槛时，按实际记录应做数、实做数、缺项、原因及证据，保留“未达标”状态交回 AGY 裁决，不得降标宣称完成。

## 四、状态文档（`status.md`，按需设置）

跨会话、多阶段或双角色协作的窗口可单独设置 `status.md`，集中维护活动期间的进度、基线、已验证范围、限制和下一步起点。

### 1. 内容与结构

`status.md` 只保留恢复工作所需摘要，不复制完整纲领、计划、日志或实验报告，也不成为新的文档层。常规字段如下：

- `**更新日期**`：`YYYY-MM-DD`。
- `**进度**`：当前阶段进度、开发分支与起点/对照基线 commit（及是否处于零提交工作区态）。
- `**当前交接**`：明确当前由谁推进、遵循哪份 `outline.md`/`plan.md`、以及何时停机交回终审。
- **阶段表**：随 `plan.md` 动态展开同步更新，列出各阶段主题与当前状态。
- `**可依赖的事实**`与`**已知费用**`（按需）：经证据确认的结论、已知限制及累计真机预算消耗。

### 2. 状态资格与维护规则

- 状态严格按实际资格区分以下七档：`待做`、`实施中`、`源码已改待验证`、`限定范围验证`、`待交付`、`完成`、`暂停`。
- 用新结论直接替换当前快照，旧过程留在 `log.md`。篇幅增长时先替换过时结论、合并重复，不挤成长段或无限附加“最新情况”。

## 五、日志文档（`log.md`）

`log.md` 按日期正序记录实际发生的工作、Bigger-Picture Overview 决策、复盘与证据；同日多条按发生次序排列，不补造具体时刻或另加流水号。

### 1. 标准条目格式

```markdown
## YYYY-MM-DD — <阶段或事项>：<本批主题>

**范围：** 对应的阶段/问题及本批边界，必要时注明基线。

**改动：** 实际修改、全局审视发现、对 `plan.md` 的动态调整或已作决定，以及必要原因。

**验证：** 方法、输入/覆盖范围、实际结果和证据位置；没有执行验证时明确说明。

**结论与限制：** 本批已证明的结果、未验证部分及影响后续工作的缺口。
```

### 2. 记录规则

- **精简与证据**：四个字段各司其职，通常各一至三句；多项独立验证可在“验证”下列短列表。详细运行数据保存在 `data/`，日志只保留复核入口、必要计数和口径，不粘贴巨量输出或完整 JSON。
- **粒度与命名**：一条对应一个有意义的工作批次或一次阶段后 Bigger-Picture Overview；有独立决策、重要失败、周期复盘或阶段交接时另起条目，不使用“最新进展”等无区分度名称。
- **区分验证层级**：严格区分源码检查、编译、条件运行、真实原生观察及独立验收；未运行写“未运行”，不能将静态判断冒充运行或精度通过。
- **不可覆盖历史失败**：影响范围、预算或结论的失败与取舍必须保留；纠正旧记录须说明纠正了什么。
- **采集资源口径**：涉及真机采集的条目须注明本批会话/尝试数、实际覆盖及累计额度变化（失败、换请求和恢复不清零），并分别说明初始化/预热、有效观测、后处理、导出量、保留量及峰值；纯源码或文档条目不填无关资源字段。
- **避免空记录与形式工具**：无新工作不追加空条目，不为日志格式新增生成器、账本或自动检查平台。

## 六、阶段演进、三类检查与交付纪律

### 1. 阶段内闭环与 Bigger-Picture Overview

每个阶段在代码改动完成后，必须完成三类自查并执行一次全局审视，再决定下一阶段的动态展开：

- **代码检查**：沿修改影响到的生产者、消费者、调用方、配置、构建和产物追踪审查（不只看 diff），逐项检查层次与适配边界、状态/资源所有权、柔性扩展性、正确性、空行呼吸感与注释含金量。
- **文档检查**：核对过期描述、跨层引用、证据链接与阶段状态；证据被删除时取消可点击入口。
- **数据检查**：核对适用环境、引用及保留范围，仅清理本任务拥有且已确认无用的临时产物，不动既有受保护资产。
- **Bigger-Picture Overview**：跳出本阶段局部视角重新俯瞰全仓，更新 `plan.md` 后续阶段与演进记录，再进入下一阶段。

### 2. 提交与推送纪律

- **零提交终审模式（自主窗口默认）**：若 `outline.md` 规定全流程不做 `git commit` / `git push`，Codex 须全程保持零提交，交付干净工作区与最终工作区 `src/` SHA-256 清单；待 AGY 终审通过并经用户确认后，再按清晰职责分层提交并推送开发分支。
- **阶段提交模式（传统分段窗口）**：三类检查完成后按职责分层提交并推送开发分支，核对暂存内容及远端实际提交，再作为下一阶段基线。
- 数据“检查完成”不表示提交数据，原有忽略范围保持不变；严禁触碰或提交用户私留的未跟踪目录与笔记文件。

## 七、窗口关闭与取消

活动计划若仍有未完成范围，不能为了整理目录擅自关闭或取消；主工作流只留其概要，实施细节继续由该窗口维护。确认关闭、提前结束或取消时，按以下四步执行：

1. **在纲领/计划页标记关闭**：核对实际结果，在 `outline.md`（传统窗口则在 `plan.md`）标题下标记 `**已关闭**`，注明关闭结论是完成、提前结束或取消以及关闭日期，按实际记录未完成的内容。
2. **向主工作流写自足总结**：包含日期和目标、主要修改与取舍、实际验证范围、结论与遗留项；保留影响后续判断的失败及证据，不复制完整日志。
3. **登记遗留去向**：将未完成事项明确记录为后续目标、范围外能力或待验证限制；确需继续执行时，另建有明确边界的新窗口。
4. **原地保留历史记录**：关闭后在原目录保留 `outline.md`（若有）、`plan.md`、`log.md` 及已有的 `status.md`，作为历史记录。设计或工程约束发生变化时，独立修订相应静态合同。
