# 技术评审 · Prologue 怎样重建与扩展

这份文档用于评审实现取舍。阶段、范围和交付口径由 [实施计划](plan.md) 规定。下面的数值和请求除明确引用原生记录外均用于走读合同。当前有状态局部采集的可行性与开销仍待实测。

| 先审的决定 | 当前方案 | 主要影响 |
| --- | --- | --- |
| 原生控制与模拟状态 | 原生代码决定动作，C++ 维护可变资源和虚拟时间，适配器只映射必要事实。 | 仿真能否保留真实调度行为，以及更换框架要维护多少东西。 |
| 结构模板的最小共享单位 | 共享局部定义与端口，父调用按真实成员和条件连接，执行实例独立绑定。 | 跨配置及模型复用会节省多少取证，父模板会不会随内部实现膨胀。 |
| 有状态局部采集的要求 | 前置状态由原生接口准备，先证明工作等价，再算启动和实际卡时。 | 能否实现单卡、低开销取证，是否需要日常维护框架状态。 |
| 规则存在哪里 | 共享受限的规则声明，结构、成本和采集的业务判定各自只有一个实现。 | 保持适配灵活，控制规则与接口数量。 |
| 验收能证明什么 | 结构、固定图成本和自主结果分别判定。纯预测与受限补采独立评价。 | 避免用结构匹配替代性能结论，保留未证实的范围。 |

## 1. 一次调用如何走完

~~~mermaid
sequenceDiagram
    participant N as 原生控制
    participant E as 核心仿真
    participant G as 结构层
    participant P as 性能层
    N->>E: 提交决定、角色和实际成员
    E->>G: 动作与共同状态视图
    G-->>E: 已绑定的工作、端口和依赖
    E->>P: 批量查询这些已知工作
    P-->>E: 自身服务时长或成本缺口
    E-->>N: 资源与完成通知
~~~

只有动作可以实例化、必需服务时间齐备时，核心才提交该动作新增的资源效果和在途工作。遇到缺口时保留已完成的前缀与原查询，恢复从原始初态建立新会话。这种重跑允许后续组批随新时间改变。

| 交接对象的拟定形态 | 生产者 → 消费者 | 评审要核对的边界 |
| --- | --- | --- |
| `Action` | 控制适配器 → 核心仿真 | 带逻辑角色、实际成员、阶段和已知进度。调用语义相同的两次执行仍有不同实例身份。 |
| `StateView`、`Completion` | 核心仿真 → 控制适配器 | 页和槽位按作用域及有效期返回。缓存所有权、就绪和虚拟时间由核心单独维护。 |
| `BoundWork` | 结构层 → 仿真与性能层 | 含已绑定工作身份、外部端口、形状、计时切口和依赖。用语义身份追溯对应原生工作。 |
| `WorkQuery` | 性能层特征入口 → 同一个 C++ 求值器 | 请求字段能追到工作产生时的真实参数。输出为有来源的纳秒值或明确缺口。 |
| `TemplateNeed`、`CostNeed`、`RuleNeed` | 各判定所有者 → 工作流 | 保留能重放的查询、真正缺的依据及受影响目标。Python 编排消费结果，业务判定在原处执行。 |

这些名字描述边界。接口可以随实际消费者合并或收紧。虚拟状态与真实状态要分两个运行过程理解。预测中的 Python 控制可以拥有请求队列和逻辑进度，通过共同状态视图使用核心的页与完成事件。真正取证时，由原生框架拥有实机分配及线程生命周期。两边都需要预测和参考一致的预热及初态，KV 驻留和工作区预分配分别核对。

**容易出错的地方**　控制适配器为方便移植再建一份模拟页表，或以宿主墙钟决定完成。评审应沿一次分配、等待、释放和重用追踪写入者，再检查缺成本停住之后是否留下这一动作的半次分配。PD 和 PP 的角色独立推进通过相同控制接口交接，互相等待通过可观察的完成边表达。

## 2. 子图怎样来，以及什么能共享

### 子图分层的实际走法

1. SGLang 适配器给出原生切口的对象、角色和参数来源。Ascend 适配器独立提供已证实的提交与服务、完成、同步和时钟依据。
2. 从切口形成带工作、资源效果及必要因果的粗图。以端口与资源读写作为切割边界。CPU 内部范围可以合并，但外部阻塞、唤醒、发布、提交和工作归属仍要可追踪。
3. 归一化把运行实例中的地址、序号、请求和物理卡编号改成可绑定参数。结构分支、语义端口、形状公式、角色限制及状态效果继续参与适用性。
4. 先匹配角色与调用条件，再绑定调用实际参数、输入输出及资源。样本相近的定义只有在可观察结构和效果等价时才共用。结构模板的粒度可以粗，性能坐标保留到可独立计量和建模的自身服务区间。

### PD 批准备的走读

SGLang 在 Decode 侧从等待队列选择准入成员、准备下一轮输入并创建原生批次。批准备读取实际槽位和前缀范围，按成员复制页表片段，还会更新请求进度的相关状态。它提供了一个具体可评审的父子边界。 [原生准入与批构造](../../../third_party/sglang/python/sglang/srt/disaggregation/decode.py#L1892) · [原生逐成员批准备](../../../third_party/sglang/python/sglang/srt/disaggregation/decode_schedule_batch_mixin.py#L25)

| 请求 | 进入这次动作 | 源槽位与区间 | 目标片段 |
| --- | --- | --- | --- |
| A | 是 | 槽位 7，[4, 6) | [0, 2) |
| B | 是 | 槽位 5，[17, 20) | [2, 5) |
| C | 仍在等待 | 本次无需绑定 | 本次无需写入 |

父调用记录自身准备、按准入列表调用两个子实例、目标切片和完整就绪条件。两个实例引用同一个复制定义，实参和效果独立。先完成哪个子实例由实际依赖和资源决定。如果只有父关系缺失，新增证据只核对成员、调用、入参、目标写入、完成和必要的父自身工作。已存在定义的内部观测可关闭，原生实际执行的子调用仍计入开销。历史案例曾出现输出形状正确、设备工作数量偏少，评审必须逐成员查图和资源效果。 [历史成员反例](../../../data/architecture-acquisition-performance/v/diagnosis/training-pd-preparation-cardinality.json)

**正反例**　变为单成员、三成员及有等待成员时分别核对真实的工作数量、源槽位、目标片段和进度。规则的输入是原生准入后的成员列表。若不同角色共享同一块可见缓冲区，必须保留写入者、数据版本和消费就绪，才能使用独立采集的局部定义。

### 换输入时怎样判复用

| 变化 | 优先保留与检查 | 必须另有依据的部分 |
| --- | --- | --- |
| 只改变请求长度、同刻分布或到达间隔 | 已声明的参数与条件，动态重新组批。 | 数据跨页、进入新分支、资源效果或工作坐标变化时的适用证据。 |
| KV 容量、页大小、chunk、缓存策略改变 | 分开检查可绑定参数、页表布局与新的原生调度路径。 | 具体实现可能变更，只有适用的子定义能交给新父调用。原生没产生目标分支时保留未验证。 |
| TP、PP、EP 或 PD 角色发生变化 | 先确认实际分片、成员与物理端点，复用已证明相同的本地工作。 | 组内或组间依赖、传输、相同逻辑角色的物理时延仍分别核对。 |
| 模型、dtype 或后端改变 | 从同实现、同语义端口和同类布局筛候选，由新模型绑定本次形状。 | 需要独立核对目标原生实现、张量布局、资源影响和性能域。只共享经证实的部分。 |

跨模型验收应选带实际计算或资源效果的子定义，并记录少了几次观测、编译或补采。单纯使用同名函数和共用空控制节点只适合作索引线索。

## 3. 性能绑定的例子和换模型的代价

以一次设备到宿主回读为例，图声明搬运的源、目的、就绪和完成，性能层接收方向、字节数、实现、设备与计时条件。样本刻画源已就绪之后的自身服务。若源工作尚未完成，等待由原始数据依赖产生。同步调用的宿主返回、队列可见时间、异步设备完成分别归到实际所需的边界。

- 回读 24 与 32 字节的记录支持在该测量条件下建立和检查局部候选。另用未参与拟合的点判断是否有资格插值。反向拷贝、未验证范围或不同分片物理域分别返回需要的成本证据。 [既有回读记录](../../../data/architecture-acquisition-performance/f2/on-demand/handoff.json)
- 对 Decode attention，应取已绑定的查询 token、已驻留 KV、头数、数据布局和执行条件。按真实服务区域测量。一组各维度的最小值和最大值只能描述样本范围，联合域要看同一执行分支的组合及训练外点。
- 添加新模型族时，框架适配器保持发布经过验证的工作和特征，Python 实现离线拟合，C++ 实现该族的统一查询。计算图、资源与验证入口继续使用相同的求值合同。模型族的引入由真实工作和训练外对照决定。
- 单卡时真分片上的本地耗时可实测。通信查询还要匹配实际拓扑、链路、角色、方向、载荷和计时范围。若没有物理证据，目标停在相应通信服务的缺口。本地分片采样可继续用于其他合格工作。

**容易出错的地方**　模型估计误差导致执行顺序改变时，固定图和自主误差需要分开解释。先在固定图保留实测结构与外部交付，检查预估自身服务。再观察自主预测中的首个组批差异。CPU 活动、通信和设备等待的误差可能同时落在一条关键路径上，恢复各类实测后的端到端差值应各自报告。

## 4. 局部采集要先证明什么

| 候选路径 | 需要的原生条件 | 对照证据 |
| --- | --- | --- |
| 重读存档或补父边界 | 既有记录能追出实际调用、条件和状态，或只需在真实父边界观察。 | 原查询选择同一子定义，端口、子调用次数及资源效果可核对。 |
| 直接测独立算子或搬运 | 适配器能准备真实实现、布局及已就绪输入。 | 同服务语义、测量区间和方向，实测产物能直接回答原工作坐标。 |
| 真实批次或 KV 的局部运行 | 上游负责创建、使用和释放批次及页。局部路径能访问与 serving 相同的执行底层。 | 同原生 serving 对照关键参数、真实状态、工作及完成边界，另记跳过了哪些服务步骤。 |
| 最短服务运行 | 需要原生生命周期才能触发工作。 | 最小可区分请求、目标分支真实触发、窗口及成本归属清楚。 |

S03 对两条困难路线做最早判断。PD 批准备先查找到候选入口时是否已有真实准入、槽位、KV 位置和释放方。attention 要追到模型的实际 kernel 路径、有效 KV、布局、提交和完成。评审时检查准备代码是否只是调用原生接口，是否在适配层重新实现了整个状态机。证据无法建立时保留停留位置和必要的原生完整路径。S07、S08 再各自实现有实际资格的入口。

把**完整请求生命周期减少**和**Engine 初始化减少**分别计数。允许复用一个已经预热的原生会话做定点采样，但仍按分摊条件如实记录启动、预热、准备、执行和回收。既有 attention 取证的有效观察约 3.84 秒，启动与预热分别约 22.90 和 48.54 秒，单看探针窗口会高估收益。只展示执行窗口缩短的结果按该能力记录，最低交付仍要求一条有状态路径在等价证据下实测减少完整启动和卡时。 [定点 attention 的历史计量](../../../data/architecture-acquisition-performance/f2/attention/handoff.json)

定向采样从缺口坐标反推候选输入。例如需求来自一个已绑定的 Decode 子图，需要特定的查询 token、KV 长度和分片布局。采样入口准备候选批次后，比较原生实际执行的坐标和服务切口。请求名义长度与实际坐标有差别时，实际合格坐标仍可另行使用，原缺口保留未命中。可在一个状态生命周期内取多个点，框架负责每点之间的合法更新或重置。

## 5. 规则、发布和重复补采

### 规则内容的评审

规则声明包括决策作用域、可见事实及其单位、条件、已登记操作和参数映射、判例与证据。图变换只引用已实现、受约束的操作。例如 PD 的准入事实包含成员和页表范围，模板可以按成员集合应用子调用及区间映射。逻辑准入本身属于控制代码。类似地，一个回读采样方法必须能够建立源就绪；获取此事实的责任在取证适配器。计划选择可构造的方法，数据进入性能库前核对本次源确实就绪。

| 类型 | 最小声明的例子 | 绑定结果的判断方 |
| --- | --- | --- |
| 模板绑定 | 在声明的批准备调用中，用原生准入范围给已注册的逐成员复制操作绑定源槽位、区间和目的端口。 | C++ 结构层按调用契约核对范围、工作数量和端口，逐成员使用同一子定义。 |
| 成本绑定 | 回读工作读方向和字节，允许使用指定测量口径下的有界曲线，物理域由工作声明提供。 | C++ 成本查询基于已发布模型和资格求值，拟合端提供训练外检验。 |
| 采样方法 | 设备到宿主回读缺时延且可以准备真实输入时，绑定字节数并选已登记的局部测量，返回就绪与服务时间证据。 | 适配器核对已经建立的实际条件，采集规划按回报的证据与费用选择方法。 |

每条规则应能回答三个问题。

1. 运行到哪一步时，哪些字段已经合法可见。来源从控制、结构、性能或适配器四处之一确定。
2. 同一输入两条规则同时产生不同结果时，系统如何指出冲突。若某个未知事实能够改变答案，保留该事实缺口。
3. 判例是否读了与正式运行相同的规则入口。原生记录提供预期行为或证据，声明的输出不充当自身正确性。

维护者和 agent 使用同一提交入口，以一个确实发生的知识缺口、一个原生正例和一个能区分错误规则的反例验收。共用格式与各类选择的语义边界分开。若需要一个新的原生观测或状态入口，明确调整哪个适配器；若是共有操作，先找实际调用方再将语义放进相应核心模块。

### 资产与补采的走读

新任务 T 先固定发布 P，若读到两个不同目标的结构缺口以及三项同域成本缺口，工作流先合并能用同一会话取证的需求。优先用保留的事实重建，局部补采的输出要复查原查询。整个任务只升级到一份已通过资格检查的发布。另一任务仍可在 P 上完成，任一发布失败时已发布对象保持可用。并发任务发现相同缺口时重新检查当前发布，以实际消耗记账。

发布指向的更新限定在本地短临界区。耗时采集和拟合先产生候选，提交时重新读取当前发布。若别的任务已补上同一需求，采用通过原查询复核的现有对象。旧任务引用的对象随原发布保留。评审发布时用一个写入到一半的候选，检查另一个任务仍能读到完整发布。

成本缺口只从已绑定工作得到。工作流可以批查取得本次动作后面已知的所有成本。后续动作还依赖原生控制和成本反馈，按新执行得到的事实继续推进。每轮记录解决的结构分支和工作坐标、原生启动次数、重跑次数和费用。反复同类缺项时先追到具体身份或状态合同，再决定是否扩大采样范围。

**容易出错的地方**　把「新增一个文件」当作覆盖增加，把一组重复的窄形状样本当作联合域扩大，或者按任务名为当前案例加规则。评审看同一原查询是不是能可靠通过、同类新请求是否零新增规则、此前的合格用法是否仍成立。局部产物的真实身份可追到采集会话及原始范围，简洁结果保留路径与状态即可。

## 6. 三条路径分别证明什么

| 路径 | 一个必须能回答的问题 | 容易造成假通过的做法与识别方式 |
| --- | --- | --- |
| 实测条件验证结构 | 把合格的真实服务与外部就绪时间交给虚拟时间线后，是否能由原生控制和模板自行得到相同的成员、工作与必要依赖。 | 真实批次或真实子图会把本应预测的事实送给系统。审核旁路消费的内容和动作身份，逐工作检查实测、区间或缺测。 |
| 真实图验证性能 | 原生图保持已知时，换入成本后出现的误差沿哪条资源或依赖传到结果。 | 基线和真实端点未对齐会混入测量误差。固定实测输入交付前的本地进度要另查，防止时间约束掩盖早到；替换后的交付等待单列。 |
| 自主预测闭环 | 用户给定目标与发布资产后，控制选择、展开及性能反馈合在一起时，实际能预测哪些请求。 | 直接用详细 profiler 墙钟作轻量参考会混入观察开销。独立参考要核对稳态、发布点和训练隔离，再按 TTFT、TPOT 的各自分母给出结论。 |

一个参考可以服务两个采集来源，阶段设计需同时列出目标数、实际请求数、原生参考数和评价数。固定图无法评分、单 token 的 TPOT 不适用、未触发和预算失败分开。纯预测和受限补采保持同一起点与真值。补采取自独立的局部训练会话，若回到同一个完整目标实测，结果单独作为辅助诊断。规则修正用到的目标须保留原冻结结果，修后从未看过的例子中取证。

建议重点看三组证据。第一组是同一结构只换成本能解释具体端点漂移。第二组是一个确实出现的多角色组合能说清可评分请求和计时资格。第三组是规模压力下每个阶段的用时。上一窗口 32 请求已经完整对照，128 请求当时取得的是局部展开证据；这两个事实对本窗口的容量预算有不同用途。 [32 请求对照](../../../data/architecture-acquisition-performance/rounds/17/development/sustained-tp2/qwen/medium-native/sustained-replay/result.json) · [128 请求局部覆盖](../../../data/architecture-acquisition-performance/rounds/17/development/sustained-tp2/qwen/case-128-staggered/local-single-coverage)

## 7. 评审时怎样判断代码有没有越层

| 改动场景 | 应修改的主要位置 | 现场可以追问的证据 |
| --- | --- | --- |
| SGLang 的原生切口或入口变了 | `integrations/frameworks/sglang` 的观测、状态视图、采样入口及受影响规则。 | 核心收到的共同动作、资源、状态合同是否仍成立。原生私有函数和版本判断是否留在适配侧。 |
| 更换设备或计时工具 | `integrations/platforms` 的部署、队列、时钟与测量范围，及新的物理成本资产。 | 同一工作开始、结束的依据是否仍可核对。时间换算有没有重复写到预测核心。 |
| 增加一种可复用的资源或依赖 | 核心结构或仿真的共同接口，适配器补充实际可见事实。 | 有哪两个真实消费者需要它。只为一个框架私有路径扩张时，优先重新审查适配边界。 |
| 新增性能模型或特征 | 性能层的求值与离线拟合，适配层补足必须采集的事实。 | 预测、补采计划、固定图是否使用同一工作坐标、适用域和求值。 |
| 增加真实流量案例或实验矩阵 | `example/` 的 workload、对照编排与汇总。 | 正式单案例核验继续通过 `verification/` 入口。耗时巨大的明细如何按条件产生和留存。 |

代码重写先沿公开用途确认旧功能的行为和失效条件。归档前查清工作区归属，S02 可将归档做成内部提交，其对外阶段交付同时具备新的可构建入口。最终干净检出须实际查加载的 Python 包、采集桥、C++ 程序、镜像和资产来源。采集证据、日志和可选明细的路径可复核，实验临时文件由实际所有者处理。
